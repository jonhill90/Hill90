# Rebuilding OpenBao from nothing, and reseeding from SOPS

`Written 2026-08-02, before execution.` Authorised by Jon after the cheap recovery path was
proven closed — see [`approle-rejection-2026-08-01.md`](../decisions/approle-rejection-2026-08-01.md)
and `vault-unseal.md`.

**This destroys the vault's barrier and every credential it holds.** Read the whole page
before running anything. The gate in Step 2 is not optional: if the restore rehearsal fails,
**stop** — a rebuild on an unproven backup has no way back.

## Why this is necessary

| Path back to root | State |
|---|---|
| `bao operator generate-root -init` | **403 permission denied** — unauthenticated root generation is disabled by default on OpenBao ≥ 2.5.3 |
| root token file `/opt/hill90/secrets/openbao-root.token` | absent |
| `VAULT_SYNC_TOKEN` | does not validate |
| all nine AppRole credentials | rejected, `invalid role or secret ID` |

The vault is healthy and unsealed. **It is also unadministrable**, and has been since
2026-07-26.

## What comes back, and what does not — verified, not assumed

The vault's file backend was enumerated read-only from the data volume. Path *names* in KV v2
are salted, so they cannot be read — but they can be **counted**, and the count is the check:

```
KV metadata entries (secret paths) : 3
KV version blobs                   : 3
AppRole roles stored               : 2
sys/policy entries                 : 6
```

**Three KV paths, and `vault.sh seed` writes exactly three** — `secret/infra/traefik`,
`secret/infra/vps`, `secret/observability/grafana` — every value sourced from
`infra/secrets/prod.enc.env`. So **no stored path lacks a SOPS source.** That was the stop
condition and it is cleared.

| Object | Comes back from | Reproducible? |
|---|---|---|
| the 3 KV paths (6 values) | SOPS, via `vault.sh seed` | **yes** |
| policies | `platform/vault/policies/*.hcl` in this repo | **yes** |
| OIDC auth config | `vault.sh setup-oidc`, secret from SOPS | **yes** |
| AppRole roles + credentials | regenerated by `vault.sh bootstrap-approles`, written back to SOPS | **yes, but the new values must be committed** |
| unseal key + root token | **new** — generated at `init` | must be stored to SOPS and the host |

**Note the AppRole discrepancy, because it is the likely explanation for #639:** the vault
stores **2** AppRole roles while SOPS holds **9** credential pairs. Whatever the nine were
issued against no longer exists.

## Rollback

**Before Step 3, rollback is: restore the volume tar and restart.** That is what Step 2
proves works.

```bash
docker stop openbao
bash scripts/backup.sh restore vault /opt/hill90/backups/vault/<timestamp>
docker start openbao
bash scripts/vault.sh unseal        # with the OLD unseal key, still in SOPS
```

**After Step 3, rollback is the same restore**, but the *old* unseal key must still be
available — so **do not overwrite `OPENBAO_UNSEAL_KEY` in SOPS until Step 6 succeeds.**
That ordering is the whole safety margin: while the old key is intact and the tar restores,
the rebuild is reversible.

**After Step 6**, the old barrier is gone and the tar is the only way back to the old vault.
Keep it.

**What is never at risk:** SOPS is the operative store and is unchanged by any of this. No
service reads OpenBao at request time — `deploy.sh` falls back to SOPS — so a broken vault
does not take the estate down. That is why this is safe to attempt at all.

## Procedure

### Step 1 — Back up the data volume

```bash
bash scripts/backup.sh backup vault
```

Record the path and byte size. A tar that exists is not a tar that restores.

### Step 2 — GATE: prove the backup restores

Restore into a **throwaway volume**, start a **throwaway OpenBao** against it, unseal with
the current key, and confirm it reports `Initialized true / Sealed false`. Then remove both.

**If this fails, STOP.** Do not proceed. Report the failure.

### Step 3 — Reinitialise

```bash
docker stop openbao && docker volume rm openbao-data && docker start openbao
bash scripts/vault.sh init
```

`init` prints a new unseal key and root token. **Do not commit them yet** (see Rollback).

### Step 4 — Unseal, policies, seed

```bash
bash scripts/vault.sh unseal
bash scripts/vault.sh policy-apply
bash scripts/vault.sh seed
```

`seed` refuses if any required key is missing from SOPS rather than writing a blank.

### Step 5 — OIDC **first**, then AppRoles. The order is load-bearing.

```bash
bash scripts/vault.sh setup-oidc          # MUST come first — see the warning
bash scripts/vault.sh bootstrap-approles
```

> **`bootstrap-approles` REVOKES the root token when it finishes**, unconditionally. With
> `generate-root` disabled, that makes it the last administrative act possible — anything
> not configured before it cannot be configured afterwards without another reinitialise.
>
> **This was learned the hard way on 2026-08-02.** The reinitialise workflow does not run
> `setup-oidc` at all, and this runbook originally listed `bootstrap-approles` first. The
> result was a rebuilt vault with working AppRoles, no OIDC auth method, and no way to add
> one — the same one-way door as 2026-07-26, recreated by the repair itself.

`bootstrap-approles` writes the new role/secret IDs back into SOPS — **that change must be
committed**, or the next deploy syncs the host checkout to `main` and reverts them.

### Step 6 — Prove it, then store the new unseal key

- AppRole login succeeds for **at least three services**
- a **deploy authenticates through OpenBao** rather than falling back
- baseline **16 containers by name, 0 unhealthy**

Only then:

```bash
bash scripts/vault.sh store-unseal-key     # writes OPENBAO_UNSEAL_KEY to SOPS
```

### Step 7 — Revoke root, and confirm the revocation

```bash
bash scripts/vault.sh revoke-root
```

`revoke-root` verifies independently that the token is dead and refuses to report success
otherwise. **Confirm that output.** A live root token on disk is the single largest standing
risk in this design.

> **Do not run `revoke-root` before Step 5 completes.** Root generation is disabled, so
> revoking early leaves a vault that cannot be configured — that is exactly how this
> situation arose on 2026-07-26.
